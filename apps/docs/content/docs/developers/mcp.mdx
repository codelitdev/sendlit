SendLit exposes the same team-scoped email capabilities through a Model Context Protocol (MCP) server over stateless Streamable HTTP at:

```text
https://api.sendlit.app/mcp
```

For a local installation, replace the origin with the API origin configured in your environment, for example `http://localhost:5000/mcp`.

## Connect and authenticate

SendLit supports both the current `2026-07-28` protocol and the existing `2025-11-25` Streamable HTTP initialize handshake. Modern clients may call `server/discover`, then `tools/list` and `tools/call`; existing clients begin with `initialize`. Every request is self-contained: there is no MCP session ID or retained server-side transport state.

The retired SSE transport is not supported. In particular, `GET /mcp` is not an MCP endpoint; clients must use HTTP `POST` to `/mcp`.

Current clients construct the protocol envelope and the `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` headers. Do not set those headers manually unless you are implementing an MCP client.

Authenticate with one of these headers:

```http
Authorization: Bearer <oauth-access-token>
```

or a team API key in `x-sendlit-apikey` (or the standard `X-API-Key`; send only one):

```http
x-sendlit-apikey: sl_live_...
```

OAuth-capable clients should discover the protected-resource metadata before starting authorization:

```text
GET /.well-known/oauth-protected-resource
GET /.well-known/oauth-protected-resource/mcp
GET /.well-known/oauth-authorization-server
GET /.well-known/openid-configuration
```

OAuth authorization, consent, token, introspection, revocation, and userinfo endpoints are provided under `/api/auth/oauth2/*`. SendLit supports pre-registered clients, Client ID Metadata Documents (CIMD), and Dynamic Client Registration (DCR). For CIMD, the OAuth `client_id` is the HTTPS URL of the client's metadata document. Modern clients should prefer CIMD; DCR remains available for existing clients such as MCP Inspector.

Use Authorization Code with S256 PKCE, request only the scopes your client needs, and keep any refresh token in the client's secure credential store. The authorization request must include an explicit, non-empty `scope`; SendLit does not turn a missing value into a full-access grant. Every authorization requires a SendLit user to sign in, select a team when necessary, and approve consent.

Team API keys always select one fixed team and can run every MCP tool and
operation for that team, except API key management (`teams.listKeys`,
`teams.createKey`, `teams.removeKey`), which requires OAuth.
Organization API keys, dashboard session cookies, and `X-Sendlit-Team-Id` are
not accepted as MCP authentication. Use the REST API for organization
discovery, shared-delivery setup, and team provisioning; see
[Headless organization setup](/developers/headless-provisioning).
Deleting an account is dashboard-only and has no MCP tool; see
[Account](/workspace/account#delete-your-account).

OAuth clients (including MCP clients like Claude) have no way to send a custom header during authorization, so a multi-team account instead picks a team as part of the OAuth flow itself: after login, and before the consent screen, the account is shown a "select a team" step (mirroring how apps like Notion resolve their own multi-workspace ambiguity). The chosen team is baked into the issued access token and used for every subsequent request — no header needed. Accounts with exactly one team skip this step entirely.

### OAuth scopes

OAuth access is default-deny per REST operation: a dedicated tool and an `api.*` call to the same operation need the same scope, and `api.list_operations` shows which scope each operation needs and whether your token has it. Read and write permissions are separate:

- `contacts:read`, `contacts:write`
- `templates:read`, `templates:write`
- `media:read`, `media:write`
- `sequences:read`, `sequences:write`
- `emails:read`, `emails:send`
- `settings:read`, `settings:write`
- `esp:read`, `esp:write`
- `teams:read`, `teams:write`
- `api_keys:read`, `api_keys:write`
- `feedback:read`, `feedback:write`
- `delivery_events:read`
- `suppressions:read`, `suppressions:write`

## Available tools

SendLit follows the CodeLit pattern: dedicated tools for the everyday flows, and five generic tools that reach every other team operation of the [REST API](/developers/api). A client loads a short catalog (34 tools), and nothing the REST API offers a team is out of reach.

### Dedicated tools

- **Contacts:** `list_contacts`, `get_contact`, `create_contact`, `update_contact`, `add_contact_tag`, `remove_contact_tag`, `import_contacts` (up to 1000 rows per call; statuses only get stricter)
- **Segments:** `list_segments`, `create_segment`. Segments save reusable filters over contact fields, tags, subscription state, signup date and custom fields.
- **Templates:** `list_templates`, `get_template`, `create_template`, `update_template`
- **Broadcasts and sequences:** `list_sequences`, `get_sequence`, `create_sequence`, `update_sequence`, `add_sequence_email`, `update_sequence_email`, `send_sequence_email_test`, `start_sequence`, `pause_sequence`, `get_sequence_stats`
- **Transactional email:** `send_email`, `get_email`, `list_emails`
- **Events and delivery:** `track_event`, `list_delivery_events`, `get_plan_usage`

Broadcasts use the sequence resource with one email and an audience filter. `update_sequence` sets a sequence's trigger, including `event:custom` with a `triggerFilter`, who can enter (`reentry`, `reentryPeriodDays`), and an `excludeFilter` whose contacts are never sent the broadcast or enrolled; see [Sequences](/email-marketing/sequences#custom-events). Send a test with `send_sequence_email_test` (a `[Test]` copy to you, or up to five addresses) and use `start_sequence` only after the audience, trigger, content, delays and tag actions are correct.

Template and sequence-email content is validated as a complete SendLit email document on every write. The `style` must include `colors`, `typography.header`, `typography.text`, `typography.link`, `interactives` and `structure`; blocks must be one of text, link, image, separator or footer. Metadata supports only optional `previewText` and an optional `utm` object with `source`, `medium` and `campaign` strings. For AI-created content, start from a system template (`templates.listSystem`, then `templates.duplicate` through the `api.*` tools) rather than constructing a document from scratch.

`send_email` sends one API-triggered email, accepts only team-owned transactional templates, and reports `template_not_transactional` or the missing variable paths without creating a send. Broadcast and sequence tools accept only marketing templates. `track_event` records a [custom event](/developers/events) and starts the sequences it triggers; send production events through the REST API, which allows far more requests per minute.

### Generic API tools

Everything else a team can do over REST runs through these tools: sending providers (ESPs) and their delivery feedback, suppressions, [sender reputation](/email-marketing/reputation), the [tracking domain](/email-marketing/tracking-domain), general and [web archive](/email-marketing/web-archive) settings, [signup forms](/email-marketing/signup-forms), media, tags, segment and template management, sequence schedules, subscribers and archiving, event definitions, contact exports and deliveries, teams and API keys, and every delete.

1. `api.list_operations` lists the operations, filtered by `search` or `group`. Each item has its `operationId`, method and path, the tool that runs it, the OAuth scope it needs, and whether this connection may run it.
2. `api.describe_operation` returns an operation's path and query parameters, the JSON Schema of its request body, and the schema of a successful response (from [`/openapi.json`](/developers/api)).
3. `api.read` runs a read operation, `api.write` an operation that creates or changes data or has an external effect (such as testing an ESP), and `api.delete` one that deletes or permanently disables something. Each takes `operationId`, `pathParams`, `query` and, for writes, `body`. `api.delete` also needs `confirm: true`: confirm the target with the person first.

A call runs exactly as the REST request would, for the connected team, with the same validation, plan limits and errors. For example, to retire an ESP: find `settings.esps.retire` with `api.list_operations`, check its parameters with `api.describe_operation`, then call `api.delete` with `{ "operationId": "settings.esps.retire", "pathParams": { "espId": "esp_…" }, "confirm": true }`.

Billing, account deletion, organization administration and team provisioning are not reachable over MCP; use the REST API with a dashboard session or an organization key.

### Errors

A failed tool call is a tool result with `isError: true` and `structuredContent` of `{ code, message, details }`. `code` is one of `validation_failed`, `not_found`, `conflict`, `forbidden`, `rate_limited`, `unauthenticated` or `internal_error`. `details.reason` carries SendLit's own error code (for example `plan_limit_reached`, `sending_paused`, `template_not_transactional`, `insufficient_scope` or `broadcast_sent`), `details.message` explains it, and plan limits keep the limit, usage and upgrade link REST returns.

API key management is refused when the caller authenticates with an API key; connect with OAuth to use it. The full API key secret is returned only when the key is created. Store it immediately; it cannot be recovered from a later listing. Delivery-feedback connections are supported for Resend, Postmark, SendGrid, Mailgun and Amazon SES; see [Amazon SES bounces and complaints](/self-hosting/amazon-ses-feedback). Releasing a SendLit suppression does not remove a provider-native suppression.

## Example client configuration

The exact configuration shape depends on the MCP client. For clients that support a URL-based MCP server entry, use:

```json
{
    "mcpServers": {
        "sendlit": {
            "url": "https://api.sendlit.app/mcp",
            "headers": {
                "x-sendlit-apikey": "${SENDLIT_API_KEY}"
            }
        }
    }
}
```

Prefer the client’s secure secret-store or environment-variable mechanism. Do not paste a live API key into a checked-in configuration file.

## Operational limits

The MCP endpoint is rate limited to 60 requests per minute. High-impact tools (`send_email`, `send_sequence_email_test`, `track_event`, `start_sequence`, `api.write` and `api.delete`) are limited to 20 requests per minute, and the REST API's own limits apply to `api.*` calls as well. A missing or invalid credential returns HTTP 401 with a `WWW-Authenticate` challenge, a missing OAuth scope returns a `forbidden` tool error with reason `insufficient_scope`, an unsupported protocol revision is rejected, and a non-JSON request returns HTTP 415. Because requests are stateless, retry only operations that are safe to repeat.
